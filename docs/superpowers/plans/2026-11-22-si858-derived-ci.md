# si#858: CI derived from the `ci build` / `ci test` leaves, with no `workflows:` entry - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A product that runs `support github workflows` and declares no `workflows: ci:` gets a generated `.github/workflows/ci.yml` that runs every unattended `ci build` / `ci test` leaf, in manifest order completed by port edges, with every red leaf reported, the report last, and every left-out leaf named.

**Architecture:** A new module `simplon.tasks.cipipeline` selects and orders the leaves and builds instances of the generated workflow classes (`simplon.model.workflowschema`, si#857). A converter in the same module turns that model into `workflowgen.Workflow`, which the existing renderer writes unchanged except for one flag (`Job.prepared`) and the refusal to overwrite a foreign file. `workflows.generate` (the `support:workflows` body) appends the derived workflow when no declared entry has the key `ci`; running that verb is the switch.

**Tech Stack:** Python 3.12+, pydantic (manifest load), firn model + templates (`./simplon.sh build model`), pytest via `./simplon.sh test suite`, mypy via `./simplon.sh test typecheck-python`.

**Spec:** `docs/superpowers/specs/2026-11-22-derived-workflows-design.md`, sections 5.1-5.4 and 7 (step 3), decisions D1-D4; plus the decisions on #858's comments and the three of 2026-11-22 below.

## Decisions this plan carries (all Marco's, 2026-11-22)

From #858's comments:
- `ci: { skip: "<reason>" }` on a command is the opt-out; a reason is required (expression rule).
- Order: a stable topological sort of the CI leaves, manifest order with "a consumer after its producer" as the only extra precedence. #448 is not a prerequisite.
- `support install` runs as each job's first kernel step after checkout when the product declares `toolchains:`.
- `Job.key` (1..1) is added to `workflow.firn` and read for GitHub's job id. No other class gets a name.
- The report is placed by a catalogue attribute `after_all` on `test:report`: last in its job, `if: always()`.
- The derivation switches on only where the product runs `support github workflows`. A derived file that would land on a file without the generated header is refused, with the file named.
- No junit check. The Allure archive is enough (netctl).

Chosen in this session (the choice list before this plan):
- **Manifest order, not today's order.** Measured: in simplon's manifest `build` comes before `test`, and `test release-notes` is not the last leaf (`test_own_workflows.py:238`). The spec's sentence "keeps simplon's release-notes last ... because it is last in the manifest" (5.2) is false, and so is section 7's "today's leaves in today's order". Both are corrected in Task 8. Order now matters only for ports: with `!cancelled()` on every leaf, an early red gate no longer hides the ones after it.
- **Preparation gates the leaves.** The docker probe, the disk preflight and `support install` get step ids. Every leaf after the first runs `if: ${{ !cancelled() && steps.<id>.outcome == 'success' && ... }}` (one clause per preparation step present), so one red preflight shows as one red step and not as fifteen. `after_all` leaves still run `if: always()`.
- **Job key `ci`.**

## Review Focus

1. **A consumer whose producer is skipped** (`ci: skip` or `unattended: false`) while the consumer stays in CI. Expected: `handoff.plan` refuses it today with "no job in this workflow produces it". The derivation must refuse it earlier, naming both leaves and the skip, because the handoff message talks about jobs the product never wrote. Test in Task 5.
2. **A product whose `ci build` / `ci test` hold no runnable leaf** (all aggregates, all skipped, or no such groups). Expected: a refusal naming the product's groups. A `ci.yml` with no step would be a green tick over nothing. Test in Task 6.
3. **A product that declares `workflows:` with other entries but no `ci` key, and a hand-written `.github/workflows/ci.yml` on disk.** Expected: the header refusal names the file and both ways out (declare it `handwritten:` under `ci`, or delete it). It must not silently overwrite the file. Test in Task 7.
4. **A declared workflow under another key whose `path:` is `.github/workflows/ci.yml`.** Expected: `_reject_duplicate_paths` refuses it over the declared and derived workflows together. Test in Task 7.
5. **The leaf a product placed under a nested group** (`ci: test: groups: lab: ...`). Expected: it is in the set, in manifest order. A selection that reads only `manifest.commands["test"]` (as `derive()` does) would drop it silently. Test in Task 5.
