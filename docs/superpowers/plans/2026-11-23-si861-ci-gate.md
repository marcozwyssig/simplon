# si#861: ci gate on an aggregate - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An aggregate under `ci build` or `ci test` says `ci: { gate: { paths, label, env } }`, and `support github workflows` derives its own workflow file: a decide job that reads the PR's changed paths and labels, and behind it one gated job that runs the aggregate's members as steps, once per head SHA, never cancelled.

**Architecture:** `simplon.manifest.load` reads the aggregate's `ci:` into a `CiGate` value on `AggregateCommand`. `simplon.tasks.cipipeline` finds the gates, takes their members out of the main and cadence selections, and derives one `Derivation` per gate (decide job + gated job) through the existing `_job`/`_to_job`/`to_workflow` path. The decide job's script is rendered by the kernel from the gate's data; path globs are translated to one ERE at derive time.

**Tech Stack:** Python 3.12+, pydantic (manifest load), firn model + templates (`./simplon.sh build model`), pytest, mypy, bash (the decide script, executed in a test).

**Spec:** `docs/superpowers/specs/2026-11-22-derived-workflows-design.md`, section 5.5 (the `gate:` bullet) and section 7 step 7 (decision D9), as corrected by the decisions on #861 (comment 7114394678) and below. Builds on `docs/superpowers/plans/2026-11-23-si860-variant-keys.md` and its code (`src/simplon/tasks/cipipeline.py`).

## Decisions this plan carries

Marco, 2026-11-23 (comment 7114394678 on #861):
1. `gate:` sits on an aggregate only; `ci: { gate: { paths, label, env } }`. Each member becomes its own step in the gated job and does not also run in the main job.
2. Own workflow file per gate; triggers PR `opened`/`reopened`/`synchronize`/`labeled` plus dispatch, never push to main. A decide job in front reads changed paths and the label.
3. Concurrency per ref, `cancel-in-progress: false` (netctl#513). Spec 5.5's "cancelled in progress" is corrected (Task 6).
4. `sources:` is #873, `merge: auto` is #874. Not here.
5. `env:` on the gate carries literals for the gated job; secrets stay with the si#833 module. `cadence:` and `timeout_minutes:` from #860 are allowed on the aggregate beside `gate:`.

Marco, 2026-11-23, choice list in this session:
6. **A Deploy member prepares.** A member that is a `Deploy` (a command of an env-first group: netctl's `down`, `up`, `seed`) gets a step id like a preparation step, and every later non-Deploy member waits for its success; the verifying members among themselves stay `!cancelled()`. This is netctl `lab.yml`'s `if: always() && steps.up.outcome == 'success'`. `stop_on_failure` is not read by the gated job (recorded: a local `test lab` keeps running after a red `up`; reopens if a product asks for local and CI to agree).
7. **One verdict per head SHA by a decide table**, no query of earlier runs:
   - `workflow_dispatch`, `schedule`: run.
   - `opened`: run iff a changed path matches.
   - `synchronize`, `reopened`: run iff a changed path matches or the PR carries the gate label.
   - `labeled`: run iff the label just added is the gate label and no changed path matches (a match already ran on `opened`/`synchronize`).
   Every verdict writes a `why`. Removing and re-adding the label runs again on purpose.

My calls (the executor posts them with the decisions in Task 0; Marco may overrule):
- **File:** `.github/workflows/ci-<aggregate words, dashed>.yml` (netctl `test lab` -> `ci-test-lab.yml`); workflow key and title = the stem. The one switch rule of `cipipeline.workflows` holds: a declared `workflows:` key equal to the stem switches off that gate file alone.
- **`paths:` are GitHub filter globs** (`**` crosses `/`, `*` and `?` do not), the syntax a reader knows from `on.pull_request.paths`. The kernel translates them into one ERE at derive time; the decide step runs `grep -qE` over the changed files. netctl's eight regexes all translate (Task 0 posts the translation).
- **The decide job runs on the product's `runner:`**, no checkout, no preparation; job permissions `contents: read`, `pull-requests: read`; `GH_TOKEN` is the run's token in that step's `env:` only.
- **The gated job** is built like the main job (preparation, members in plan order with `after_all` members last, report upload, cleanup), plus `needs: decide`, `if: needs.decide.outputs.run == 'true'`, job `env:` from the gate, job `timeout-minutes` from the aggregate, `concurrency: { group: <stem>-${{ github.ref }}, cancel-in-progress: false }` on the job (the decide job is never queued).
- **Members** are the aggregate's plan leaves (`Manifest.plan_tree_for`, so a member aggregate such as netctl's `build` contributes its leaves, deduplicated). An `after_all` member (the report) stays in the main and cadence runs too: it is a verdict over each run it ends, as #860 already treats it. A leaf in two gates runs in both files; no rule.
- **`cadence:` on the gate** adds a `schedule` trigger to the gate's own file (`nightly` -> `17 2 * * *`, a cron string -> itself, `manual` -> nothing beyond dispatch); the gate never moves into `ci-nightly.yml`.

## Review Focus

1. **A gate member consumes an artifact a main-job leaf produces** (or the reverse). Artifacts do not cross workflow files. Expected: refused by `_refuse_consumers_of_absent_producers` naming both and the file each runs in, unless the artifact has a `registry:`. Test in Task 3.
2. **Every unattended leaf of `ci build`/`ci test` is a gate member.** Expected: `_nothing_to_run` names the gate file(s) the leaves went to, the same way it names cadence files. Test in Task 3.
3. **A glob with ERE metacharacters** (`deploy/env/*/lab.yml`, `a+b/**`, `x(1)/*`). Expected: `.`, `+`, `(`, `)` escaped; `**/` matches zero or more directories; `*` never crosses `/`. Test in Task 4.
4. **A `labeled` event for some other label**, and a PR opened with the gate label already set. Expected: run=false with a `why` naming the label; the open-with-label case runs exactly once (on `labeled`, not on `opened`) when no path matches, and once on `opened` when one does. Test in Task 5, executing the rendered script.
5. **`env:` that clashes with the runner kind's env, or carries `${{ secrets.X }}`.** Expected: the clash is `workflowgen._with_runner_env`'s existing refusal; a `${{` value is refused at load, pointing at the si#833 secrets module. Tests in Tasks 2 and 5.
