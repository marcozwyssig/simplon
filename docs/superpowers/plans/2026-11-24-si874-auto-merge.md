# si#874: `merge: auto` derives an auto-merge workflow with netctl's seven rules - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A product writes `merge: auto`, and `support github workflows` derives `.github/workflows/auto-merge.yml`, which squash-merges a pull request labelled `auto-merge` once every gate for its head commit is green, keeping all seven of netctl's measured rules.

**Architecture:** A new top-level manifest section `merge:` (one value, `auto`), read by `simplon.manifest.merge`, its schema in `manifest.firn`. The merge policy (label, method, rules) is a firn instance in `automerge.firn`, and a template generates the script from it. The auto-merge workflow goes through firn like every generated file (Marco, 2026-11-24: "Egal was generiert wird. Es muss immer über firn passieren."): the vocabulary it needs (the `workflow_run` and `pull_request_target` triggers, workflow permissions, the kernel step `auto-merge`) is modelled in `workflow.firn` and regenerated with `./simplon.sh build model`; `simplon.tasks.automerge.derive` produces a `workflowschema` model instance (key `auto-merge`), and the existing renderer path (`cipipeline.to_workflow` / `_to_job`, as si#861's decide job) writes it. The kernel step `auto-merge` renders the generated `MERGE_SCRIPT`. `cipipeline.workflows()` adds the derivation under the one switch rule (a declared `workflows: auto-merge:` switches it off). The script is tested the way si#861's decide script is: rendered, run by bash with a fake `gh` on `PATH`.

**Tech Stack:** Python 3.12+, bash, `gh`, GitHub Actions (`workflow_run`, `pull_request_target`), pytest, mypy.

**Spec:** `docs/superpowers/specs/2026-11-22-derived-workflows-design.md` section 5.5 (`merge: auto`), narrowed by #874's body (Marco, 2026-11-23: a fixed policy, no parameters) and the decisions below.

## Decisions this plan carries

Marco, #874 body (2026-11-23): a fixed policy, no parameters; label `auto-merge` and method squash become parameters only when a second product needs another value. The seven rules, from netctl's `auto-merge.yml` (Marco's comment on #861, 2026-11-22):
1. Token scope first (netctl#964): if `gh api repos/$REPO/pulls?state=open&per_page=1` fails, fail red with "token scope problem, NOT 'nothing to merge'".
2. Only an open PR for the head branch carrying the label `auto-merge`; none is a green no-op.
3. Head == run SHA, else no merge (the newer commit merges on its own run).
4. Every non-schedule run of each gated workflow for that SHA is completed/success; a running or red one blocks. Gated workflows are triggers, so the merge is reconsidered when they complete.
5. A gate's own `label:` takes the role of netctl's `needs-lab`: a PR carrying it with no non-schedule run of that gate's workflow for the SHA does not merge; hint `gh workflow run <gate file> --ref <branch>`.
6. `gh pr merge <n> --squash --delete-branch`.
7. Dispatch the CI workflow on the base branch after merging; a failed dispatch is red ("MERGED ... UNVERIFIED").

Marco, 2026-11-24, choice list in this session:
8. **An inline script, not a kernel command.** The job runs in the privileged `workflow_run` context with a write token; no repository code runs there (no checkout, no launcher). Precedent: si#861's decide job.
9. **The label itself also triggers.** `pull_request_target: types: [labeled]`, job runs only when the label added is `auto-merge`. A deviation from netctl, written as its own rule in the rendered file's comment.

Measured 2026-11-24: a `pull_request` run of simplon's derived `ci.yml` carries `head_sha` = the PR's head commit and `head_branch` = the PR branch (run for #884: afb3c87 = PR head afb3c87). So rule 3 holds for pull_request runs as for netctl's push runs.

My calls (the executor posts them on #874 in Task 0; Marco may overrule):
- **Placement:** top-level `merge: auto` (the spec calls it a product-level datum). Any other value is a load-time diagnosis naming `auto`.
- **Rule 4 covers the CI workflow too**, not only the gates: every non-schedule run of every trigger workflow (the CI workflow and each gate's workflow) for the SHA must be completed/success, and at least one run of the CI workflow must exist. netctl's script checks only the Lab, so a green Lab could merge while CI for the same SHA was red; with the label trigger (decision 9) there is no triggering run at all, so the CI run has to be asked for.
- **Rules 2 and 3 select by SHA:** list the open `auto-merge` PRs for the branch with their head SHAs; merge the one whose head is the SHA. Labelled PRs exist but none at the SHA: rule 3's "moved on" message. This also keeps a fork PR with the same branch name from being picked.
- **Trigger workflows:** the CI workflow (derived `ci`, or the product's own `workflows: ci:` entry) and every gate's workflow (derived `ci-<words>` or declared), by their `name:`, since `workflow_run.workflows` matches names. Cadence workflows (nightly, manual, scheduled) are not triggers.
- **Rule 7's target:** the CI workflow's file (`ci.yml` when derived). If that workflow has no `workflow_dispatch` trigger, derivation is refused (diagnosis: rule 7 could not dispatch it, the way out is adding the trigger). `merge: auto` with no CI workflow at all (neither derived nor declared) is refused: nothing gates the merge.
- **Event filter:** `workflow_run` with `conclusion == 'success'` and `event != 'schedule'`; `pull_request_target` with `github.event.label.name == 'auto-merge'`. The post-merge dispatch runs on the base branch, which no open PR has as head: a no-op, no loop.
- **Concurrency:** group `auto-merge-<head branch>`, `cancel-in-progress: false`, so a CI and a gate completing together for one SHA queue; the second finds the PR merged and is a no-op.
- **Permissions** (workflow level, each with netctl's reason in the rendered comment): `contents: write`, `pull-requests: write`, `actions: write` (rule 7's dispatch, netctl run 30950192001), `issues: write` (GitHub closes the linked issues as the merging actor, netctl#1429). Token: `${{ github.token }}`; `GH_REPO: ${{ github.repository }}` (no checkout).
- **Runner:** the product's runner, as the decide job gets it.
- Not measured: netctl's note that the repository's default workflow permissions must be write for the `permissions:` block to take effect. The docs record it as netctl's prerequisite, unmeasured here.

## Review Focus

1. **A token that cannot read pull requests.** Expected: red with "token scope problem, NOT 'nothing to merge'", never a green "nothing to merge" (Task 2, `test_token_without_pull_request_read_is_red`).
2. **The label added after CI is already green.** Expected: merges on that event without a new run, but only when a CI run for the head SHA exists and every trigger run for it is green; with no CI run, no merge and the reason said (Task 2, `test_label_event_needs_a_ci_run_for_the_sha`).
3. **CI and a gate completing together for one SHA.** Expected: the two runs queue (concurrency group per branch, no cancel); the second sees no open labelled PR and is a green no-op (Task 3 asserts the group; Task 2 `test_already_merged_is_a_no_op`).
4. **A gate whose decide job said "skip".** Expected: its successful run counts as green; a PR carrying that gate's `label:` with no run of that gate for the SHA does not merge and names the dispatch command (Task 2, `test_gate_label_without_gate_run_blocks`).
5. **Two open labelled PRs with one branch name (a fork).** Expected: only the one whose head is the SHA is merged (Task 2, `test_selects_the_pr_whose_head_is_the_sha`).
