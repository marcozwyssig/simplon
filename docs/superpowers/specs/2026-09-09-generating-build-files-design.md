# Generating CMakeLists and Solution files

**Status:** design, not built. **Date:** 2026-09-09. **Ticket:** si#102.

## The goal

A C++ or .NET product on this kernel does not write its `CMakeLists.txt`, its directory includes, its
`.sln` or its `.csproj` by hand. It declares its parameters, and the kernel writes them from the tree.

This is the second half of si#95. The first half runs a pinned toolchain over a product tree; this one
produces the files that toolchain compiles. They meet in the tree and nowhere else - two coordinates, no
new subsystem.

## The two decisions, taken before the design (Marco, 2026-09-09)

**Generated files are COMMITTED.** They live in the repository, appear in diffs, and are reviewable, and
an IDE opens the project without a generator run first - which for .NET is close to mandatory. The price
is named rather than discovered: the output must be DETERMINISTIC, or every run churns the diff and the
review value is gone. For `.sln` that means stable GUIDs (section 4).

**The generator always overwrites, and every file says so.** A `DO NOT EDIT - generated by ...` header on
each. The generator is the single truth; a hand edit is reverted on the next run and the diff is where
that becomes visible. This is deliberately NOT `support:toolchain`'s never-clobber rule (si#101), and the
difference is the subject: a manifest is a product's own statement, a `CMakeLists.txt` is a rendering of
one. Reverting a statement would be wrong; reverting a rendering is the point.

## 1. Two coordinates, both placements

```yaml
  build:cmake-files:
    impl: simplon.tasks.buildfiles:cmake
    help: "Write this product's CMakeLists.txt files from its source tree."
  build:dotnet-solution:
    impl: simplon.tasks.buildfiles:dotnet
    help: "Write this product's .sln and .csproj files from its source tree."
```

Placements rather than families, unlike `toolchain:run` beside them, and the reason is not symmetry but
meaning: generating a build file is a `build` act and belongs nowhere else. `toolchain:run` had to be a
family because `ctest` and `dotnet test` belong under `test`; nothing here does.

Declared, not placed. A product without the language never sees the command.

## 2. The derivation: tree first, manifest overrides

The tree is read as the declaration. What the manifest carries is the exception, in the same shape the
argv rule uses in si#95 - default from the kernel, override where the product must.

**C++, from the tree:**

| tree | becomes |
|---|---|
| `src/<name>/` with sources, no `main.cpp` | `add_library(<name> ...)` |
| `src/<name>/` containing `main.cpp` | `add_executable(<name> ...)` |
| `tests/<name>_test.cpp` | one `add_test` per file, wired to ctest |
| any directory with sources | its own `CMakeLists.txt`, reached by `add_subdirectory` |

**The override, and it exists because ONE thing is not readable from a directory** - what a target
depends on:

```yaml
build:
  toolchain: { language: cpp, version: "19" }
  targets:
    net: { depends: [core], include: [vendor/asio/include] }
```

Guessing dependencies from include paths was considered and rejected: it reads a C++ preprocessor
approximately, and an approximate answer in a build file is worse than a declared one, because it fails
at link time in a message about symbols rather than about the manifest.

**.NET, from the tree:** each directory holding a `.cs` file and no parent project becomes one
`.csproj`; a directory under `tests/` becomes a test project; all of them become one `.sln`. Project
references come from the same `targets:` block.

## 3. What the header says, and why every file gets one

```
# Generated by cppdemo support cmake-files. DO NOT EDIT - your changes are reverted on the next run.
# What this file renders lives in cppdemo.yaml and in the tree beside it.
```

Two sentences because two questions follow a surprise: what overwrote this, and where do I change it
instead. A header answering only the first sends the reader looking.

## 4. Determinism, which the committed decision makes load-bearing

**Ordering is sorted, everywhere.** Sources, targets, projects, configuration rows. A directory listing
is not an order.

**GUIDs are derived, never generated.** `uuid5` over a fixed namespace and the project's path relative
to the product root, so the same project yields the same GUID on every machine and every run. A random
`uuid4` would put a new GUID in the diff each time and make the committed decision unusable within a
week. The project TYPE GUIDs are Microsoft's fixed constants and are quoted as such.

**A test asserts this directly**: generate twice into two directories, and the bytes must be equal.

## 5. Where it stops, and what that costs

The shapes above are it: libraries, executables, test projects, and dependencies between them. Not in
scope, and each would be a ticket with a product behind it: per-configuration compiler flags, install
rules and packaging, custom build steps, generators (protobuf, moc), multi-targeting, NuGet package
references beyond project references, and anything that needs a `PropertyGroup` a table cannot express.

The honest measurement from si#107, taken while writing the .NET chapter: a two-project solution is 54
lines, five GUIDs and 24 configuration-matrix rows. That is the size of what this generates - it is
tedious rather than deep, which is exactly why generating it is worth it and why the depth limit above
is not a temporary shortcut.

**The escape hatch, and it must exist from the first version:** a product that outgrows the table keeps
its hand-written files and does not place the coordinate. Nothing degrades; it simply does what every
product does today.

## 6. Tests

- **Determinism**: two runs produce byte-identical output. This is the one that makes the committed
  decision safe, so it is first.
- **The tree is read as declared**: a library directory, an executable directory, a test directory, and a
  nested one, each producing the expected construct.
- **The override wins**: `depends:` reaches `target_link_libraries` and a `ProjectReference`.
- **A dependency the tree does not show is not invented**: a target with no `depends:` links nothing.
- **The header is on every file**, and a file without one is a finding.
- **GUIDs are stable across runs and across product roots**, and two projects never collide.
- **Overwriting is real**: a hand-edited file is replaced, and the run says which files it wrote.
- **End to end, and this is the one 0.8.0 did not have**: generate into a scaffolded product, then run
  `build compile` through `toolchain:run` and get a binary. A generator whose output does not compile is
  not tested.
